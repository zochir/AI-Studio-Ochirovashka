# AI Comic Studio — план разработки до проверяемого результата

## Цель продукта
Android-приложение, которое превращает сюжет в редактируемый комикс с настоящими изображениями, повторяющимися персонажами, сохранением проектов и экспортом. Текстовая раскадровка или успешная сборка APK сами по себе не считаются готовым продуктом.

## Принципы работы
1. Работать от проверяемых критериев готовности, а не от списка написанных функций.
2. Не объявлять реальную генерацию проверенной по мокам, синтаксическим тестам или наличию кнопки.
3. Каждый цикл: воспроизвести проблему → найти первопричину → исправить → выполнить автоматические проверки → проверить реальный сценарий, когда доступен провайдер → записать результат.
4. При блокере продолжать независимую работу, одновременно чётко фиксируя, что именно требует внешнего доступа.
5. Не расходовать генерации на случайные пробы: сначала один кадр, затем сохранение/повторная загрузка, потом последовательность кадров.
6. Бесплатность трактовать честно: локальная генерация не требует оплаты за запросы, но требует совместимого компьютера/GPU и настройки; удалённые API могут иметь лимиты, плату или обязательную авторизацию.
7. Секреты и API-ключи не запрашивать в переписке и не записывать в репозиторий.

## Текущее подтверждённое состояние
- Android APK собирается в GitHub Actions.
- Проверки JavaScript, редактора и сценариев с имитацией API проходят.
- Есть UI для раскадровки, Images API, Pollinations, ComfyUI, сохранения/загрузки и экспорта.
- Базовый ComfyUI workflow создаётся автоматически по установленной checkpoint-модели.
- **Не подтверждено:** реальная генерация из приложения с настоящей моделью/провайдером; стабильность внешности персонажа между кадрами; установка и end-to-end работа на физическом Android-устройстве.
- Автособранный базовый workflow не использует reference conditioning, поэтому сам по себе не гарантирует идентичность персонажа.
- Прямые запросы из WebView к сторонним API могут блокироваться CORS/авторизацией. Это нужно проверить и решить архитектурно, а не считать пользовательской ошибкой.

## Этапы и критерии приёмки

### Этап 0 — зафиксировать базу и риски
- Проверить последнюю сборку и тестовые журналы.
- Проверить, откуда WebView загружает интерфейс, какие разрешения/сеть включены и как хранятся изображения.
- Составить карту: функция → реализация → тест → статус.
**Приёмка:** актуальный commit и APK однозначно связаны; список подтверждённого и неподтверждённого зафиксирован.

### Этап 1 — надёжный путь к настоящей генерации (первый приоритет)
- Сначала выбрать один основной путь: локальный ComfyUI API для пользователя с совместимым компьютером; внешний Images API как альтернативный адаптер.
- Проверить реальный запрос, получение байтов изображения, отображение в панели и понятную ошибку при отказе.
- Убрать предположение, что HTTP 200 означает валидное изображение: проверять тип/размер ответа и ошибки провайдера.
- Если WebView/CORS/доступ к локальной сети мешает, решить это через нативный Android-мост или небольшой серверный адаптер; не добавлять бесконечно новые прямые endpoint'ы.
**Приёмка:** один реальный кадр, созданный подключённой моделью, виден в приложении и переживает сохранение/загрузку. Мок-тест отдельно маркируется как мок.

### Этап 2 — повторяемость и сохранность проекта
- Сохранение сюжета, карточек персонажей, workflow/провайдера, изображений и состояния кадров.
- Безопасный импорт/экспорт проекта; большие data URL не должны бесшумно теряться или переполнять localStorage.
- Повтор только неудачных кадров без уничтожения уже готовых.
**Приёмка:** создать кадр → сохранить → закрыть/перезапустить → открыть проект → изображение и редактируемые данные на месте.

### Этап 3 — визуальная непрерывность
- Отделить «описание персонажа» от описания текущей сцены.
- Поддержать загрузку референса и реально подключённый reference conditioning (например, совместимый IPAdapter/workflow); не показывать, что референс работает, если workflow его игнорирует.
- Стабильные seed помогают воспроизводимости, но не гарантируют одинаковое лицо. Проверить минимум 3 последовательных кадра на одном персонаже; если модель/workflow не держит идентичность, обозначить это ограничение и подобрать совместимый workflow.
**Приёмка:** визуально проверенная серия из 3 кадров с сохранением узнаваемости персонажа и костюма; не только проверка текста промпта.

### Этап 4 — редактор и экспорт
- Редактирование названия, сцены, диалога; понятное состояние «изображение ещё не создано».
- Проверить SVG, PNG и HTML-экспорт на реальных сгенерированных изображениях, включая перенос/встраивание изображений.
**Приёмка:** экспортированный файл открывается вне приложения и содержит изображения, а не только подписи/пустые блоки.

### Этап 5 — Android и выпуск
- Собрать debug APK на актуальном commit.
- Установить/запустить в Android-эмуляторе; проверить доступ к файлам, загрузку референса, сеть, поворот/возврат в приложение.
- Проверить на физическом устройстве, если доступно; если нет — явно указать это.
- Проверить лицензии моделей, библиотек и провайдера перед коммерческим использованием.
**Приёмка:** автоматические тесты + проверенный end-to-end сценарий + APK, связанный с commit и контрольной суммой.

## Порядок выполнения
1. Этап 0 — аудит текущего кода и окружения.
2. Этап 1 — добиться одного реального изображения.
3. Этап 2 — доказать сохранность изображения в проекте.
4. Этап 3 — проверить последовательность персонажа.
5. Этап 4 — проверить экспорт.
6. Этап 5 — финальная сборка и выпуск.

Не делать косметические улучшения или новые функции в обход незакрытого этапа. Если для реального теста требуется недоступный локальный сервер, GPU или ключ провайдера, закончить всю независимую подготовку, дать один точный шаг для предоставления доступа и не объявлять этап пройденным.
